# IDEA 앱 고도화 진행 가이드

## 1. 문서의 목적

이 문서는 현재 IDEA 역극 채팅 앱을 **소수 지인의 실사용 앱**에서 **외부 사용자를 받을 수 있는 안정적인 비공개 베타** 수준으로 고도화하기 위한 실행 기준이다.

이번 고도화에서 결제, 요금제, 구독, 유료 기능 제한은 다루지 않는다. 지금의 우선순위는 사용자가 안심하고 계정을 만들고, 방에 참여하고, 캐릭터로 대화하며, 기록을 잃지 않고 다시 접속할 수 있게 만드는 것이다.

## 2. 최종 목표

> 현재 기능과 사용자 데이터를 보존하면서 IDEA 앱을 10개 팀, 동시 사용자 30명, 누적 사용자 100명 규모의 비공개 베타를 안정적으로 운영할 수 있는 수준으로 고도화한다.

목표가 완료되었다고 판단하려면 다음 조건을 모두 만족해야 한다.

- 주요 사용자 여정이 모바일과 데스크톱에서 정상 동작한다.
- 메시지 전송·수신·수정·읽음 표시가 재접속과 일시적인 네트워크 단절 뒤에도 수렴한다.
- 사용자가 권한 없는 방, 캐릭터, 메시지, 파일, 관리자 기능에 접근할 수 없다.
- 데이터베이스 변경은 재현 가능한 마이그레이션으로 관리된다.
- 치명적인 작업에는 확인, 오류 안내, 재시도 또는 복구 수단이 있다.
- 핵심 흐름에 자동 테스트가 있고 배포 전에 자동 검증된다.
- 운영자가 장애와 악용을 파악하고 최소한의 대응을 할 수 있다.
- 신규 사용자가 별도 설명 없이 가입부터 첫 대화까지 완료할 수 있다.

## 3. 범위

### 포함

- 인증과 계정 생명주기
- 방 생성·초대·입장·퇴장·권한
- 캐릭터 생성·편집·보관·방 공유
- 메시지, 이미지, 챕터, 북마크, 읽음 상태
- Realtime 연결, 재연결, 중복 이벤트 처리
- 알림과 PWA 설치·업데이트
- 배경음, 장소, 공유 메모, 커뮤니케이션 기록
- 관리자 화면과 운영 도구
- Supabase 스키마, RLS, Storage, Edge Function
- 접근성, 반응형 화면, 성능, 오류 처리
- 자동 테스트, 배포 검증, 백업·복구 절차
- 개인정보 보호, 신고·차단·탈퇴 같은 기본 안전 기능

### 제외

- 결제 대행사 연동
- 요금제 및 구독 상태 관리
- 유료 기능 잠금
- 청구서, 환불, 세금 처리
- 매출 최적화 실험
- 위키 앱과의 직접 연결
- 기능과 무관한 대규모 디자인 전면 교체

제외 항목을 구현해야만 진행할 수 있는 구조를 만들지 않는다. 이후 결제를 붙일 수 있도록 권한과 기능 플래그의 경계만 깨끗하게 유지한다.

## 4. 현재 코드 기준 핵심 판단

- 프런트엔드는 React 19, Vite 8, Supabase 기반의 단일 페이지 앱이다.
- `src/pages/Room.jsx`가 약 2,400줄로, 데이터 조회·Realtime·입력·표시·부가 도구가 한곳에 집중되어 있다.
- 관리자 앱과 다수의 신규 마이그레이션이 아직 커밋되지 않은 상태다.
- `build`와 `lint`는 있지만 테스트 명령과 테스트 프레임워크는 없다.
- 배포는 `main` 푸시 후 GitHub Pages로 진행되며 앱과 관리자 빌드를 함께 배포한다.
- 신규 마이그레이션에는 RLS와 `security definer` 함수가 있으므로 권한 회귀 검사가 특히 중요하다.
- README의 데이터베이스 설명이 실제 마이그레이션 보유 상태와 맞지 않는다.

따라서 현재 변경을 먼저 보존하지 않은 채 구조 개편을 시작하거나, `Room.jsx`를 한 번에 다시 작성하거나, 실제 DB에 수동으로 먼저 변경하는 작업은 금지한다.

## 5. 작업 원칙

### 5.1 사용자 데이터 우선

- 기존 테이블과 컬럼을 즉시 삭제하거나 이름을 바꾸지 않는다.
- 파괴적 변경은 `추가 → 병행 기록 → 데이터 이전 → 읽기 전환 → 검증 → 제거` 순서로 나눈다.
- 데이터 이전 전에는 영향 행 수와 되돌리기 방법을 기록한다.
- 이미지와 메시지 삭제는 UI에서 즉시 사라지더라도 서버 처리 실패 여부를 사용자에게 알린다.

### 5.2 작은 단위 변경

- 한 작업은 하나의 사용자 문제 또는 하나의 내부 경계만 해결한다.
- 기능 변경과 대규모 코드 정리를 같은 커밋에 섞지 않는다.
- 기존 동작을 설명하는 테스트를 먼저 만든 뒤 구조를 바꾼다.
- 큰 화면 파일은 새 파일로 기능을 옮기는 방식으로 점진 분리한다.

### 5.3 서버 권한이 진실의 원천

- 화면에서 버튼을 숨기는 것은 보안 수단으로 간주하지 않는다.
- 모든 읽기·쓰기 권한은 RLS 또는 검증된 서버 함수에서 강제한다.
- 사용자 ID, 방장 여부, 방 참여 여부를 클라이언트 입력만 믿지 않는다.
- `service_role` 키와 Web Push 비밀키는 클라이언트 번들에 절대 포함하지 않는다.

### 5.4 실패를 정상 흐름으로 취급

- 느린 네트워크, 오프라인, 탭 절전, 중복 클릭, Realtime 재접속을 항상 고려한다.
- 저장 중, 성공, 실패, 재시도 상태가 사용자에게 보여야 한다.
- 낙관적 UI를 사용할 때 서버 거절 시 원래 상태로 되돌릴 수 있어야 한다.
- 동일 요청이 두 번 실행되어도 데이터가 중복 생성되지 않도록 한다.

### 5.5 측정 가능한 완료

- “개선함”이 아니라 재현 절차와 통과 조건으로 완료를 판단한다.
- 수정 전 실패 사례를 남기고 수정 후 같은 절차로 확인한다.
- 실제 배포 환경에서 최소 한 번 검증하지 않은 작업은 완료로 간주하지 않는다.

## 6. 단계별 실행 계획

## 0단계 — 기준점 확보와 현황 고정

목표는 현재 작업을 잃지 않고 이후 변경을 비교할 수 있게 만드는 것이다.

### 작업

- 현재 수정·신규 파일을 기능별로 분류한다.
- `dist`, `dist-admin`, `output`, `tmp`가 소스인지 산출물인지 판단하고 `.gitignore`를 정리한다.
- 관리자 기능, 배경음, 북마크, 장소·메모, 플레이리스트 변경을 각각 별도 커밋 후보로 나눈다.
- 현재 프로덕션 URL, Supabase 프로젝트, 배포 브랜치, 필수 시크릿 목록을 기록한다.
- 현재 DB 스키마와 저장소 정책을 내보내 로컬 마이그레이션과 차이를 확인한다.
- 핵심 화면과 주요 사용자 흐름의 기준 스크린샷 또는 짧은 녹화를 남긴다.
- README를 현재 구조에 맞게 고친다.

### 완료 조건

- 의도하지 않은 미추적 파일이 없다.
- 모든 현재 기능 변경이 설명 가능한 커밋으로 보존된다.
- 새 환경에서 저장소와 문서만으로 앱·관리자 앱을 빌드할 수 있다.
- 실제 DB와 마이그레이션의 차이 목록이 존재한다.

## 1단계 — 핵심 채팅 신뢰성

가장 먼저 사용자가 체감하는 메시지 신뢰성을 안정화한다.

### 메시지 전송

- 클라이언트 요청 ID를 사용해 중복 전송을 방지한다.
- 전송 상태를 `전송 중 / 전송됨 / 실패`로 구분한다.
- 실패 메시지는 내용을 유지한 채 다시 보낼 수 있게 한다.
- 연속 클릭, Enter 중복, 느린 업로드 중 재전송을 검사한다.
- 이미지 업로드 성공 후 메시지 저장 실패 시 고아 파일 처리 방침을 정한다.

### Realtime 수신

- 초기 조회와 Realtime 구독 사이에 발생한 메시지가 누락되지 않게 한다.
- 같은 메시지가 초기 조회와 Realtime에서 모두 들어와도 한 번만 표시한다.
- 채널 상태가 끊기면 재구독하고 서버의 최신 상태를 다시 조회한다.
- 화면 복귀, 탭 활성화, 네트워크 온라인 전환 시 보정 조회를 수행한다.
- 오래된 비동기 요청이 새 방의 상태를 덮어쓰지 않게 취소 또는 세대 번호를 사용한다.

### 읽음 표시

- 읽음은 화면의 로컬 추측이 아니라 DB의 사용자별 읽음 위치를 기준으로 한다.
- 마지막으로 읽은 메시지 ID 또는 서버 시각을 방 구성원별로 저장한다.
- 방 진입, 창 포커스 복귀, 최신 메시지 노출 시 읽음 위치를 갱신한다.
- Realtime 이벤트를 놓쳐도 주기적 보정이나 포커스 복귀 조회로 최종 상태가 맞아야 한다.
- 여러 기기에서 접속할 때 읽음 위치는 뒤로 가지 않고 앞으로만 이동해야 한다.

### 완료 조건

- 두 계정, 두 브라우저로 100회 메시지 송수신 시 누락·중복이 없다.
- 발신자 화면의 읽음 표시가 수신자 열람 후 재접속을 포함해 정해진 시간 안에 일치한다.
- 오프라인에서 전송을 시도했을 때 내용이 유실되지 않고 실패 또는 재시도 상태가 보인다.
- 탭을 5분 이상 백그라운드에 둔 뒤 복귀해도 최신 상태로 수렴한다.

## 2단계 — 인증, 권한, 데이터 보안

### RLS 전수 검사

테이블마다 아래 네 가지를 각각 확인한다.

- 누가 조회할 수 있는가
- 누가 생성할 수 있는가
- 누가 어떤 행을 수정할 수 있는가
- 누가 어떤 행을 삭제할 수 있는가

특히 다음 공격을 자동 테스트한다.

- 비회원이 데이터에 접근
- A방 구성원이 B방의 메시지·메모·캐릭터를 조회
- 일반 사용자가 방장 전용 설정을 변경
- 타인의 캐릭터나 북마크를 수정·삭제
- 일반 사용자가 관리자 RPC를 호출
- Storage 경로를 추측해 타인의 파일을 읽거나 덮어쓰기

### `security definer` 함수

- 모든 함수에 고정된 `search_path`를 설정한다.
- 함수 내부에서 `auth.uid()`와 대상 리소스 권한을 재검증한다.
- 불필요한 `PUBLIC` 실행 권한을 제거한다.
- `authenticated` 전체에 실행 권한을 주더라도 함수가 관리자 여부를 자체 검증하는지 확인한다.
- 인자로 받은 사용자 ID를 호출자의 신원으로 사용하지 않는다.

### 인증과 계정

- 가입, 로그인, 로그아웃, 만료 세션, 비밀번호 재설정 흐름을 검증한다.
- 탈퇴 시 DB 레코드, 파일, Push 구독의 처리 정책을 정한다.
- 로그아웃 시 민감한 로컬 상태와 Realtime 채널을 정리한다.
- 관리자 앱은 별도 URL뿐 아니라 서버 권한으로도 차단한다.

### 파일 업로드

- MIME 유형, 크기, 확장자, 실제 콘텐츠 검증의 책임 위치를 정한다.
- 업로드 경로에 사용자 또는 방 소유권을 검증할 수 있는 구조를 사용한다.
- 공개 버킷 사용이 필요한지 재검토하고, 사적인 자료는 서명 URL을 사용한다.
- 동일 경로 덮어쓰기 권한과 삭제 권한을 별도로 검사한다.

### 완료 조건

- 권한 테스트 표의 모든 허용·거부 사례가 자동으로 통과한다.
- 브라우저 개발자 도구에서 직접 API를 호출해도 권한 우회가 되지 않는다.
- 클라이언트 번들 및 저장소 이력에 서버 비밀키가 없다.
- 탈퇴와 데이터 삭제 범위가 문서화되어 있다.

## 3단계 — 구조 개선

구조 개선의 목적은 파일을 작게 만드는 것이 아니라 변경의 영향 범위를 줄이는 것이다.

### 권장 경계

```text
src/
├─ features/
│  ├─ auth/
│  ├─ rooms/
│  ├─ characters/
│  ├─ messages/
│  ├─ read-receipts/
│  ├─ presence/
│  ├─ world/
│  ├─ audio/
│  └─ notifications/
├─ components/
│  └─ ui/
├─ hooks/
├─ lib/
└─ pages/
```

### `Room.jsx` 분리 순서

1. 순수 계산 함수와 상수를 별도 파일로 이동한다.
2. 서버 조회·변경을 기능별 API 모듈로 이동한다.
3. Realtime 구독을 기능별 훅으로 이동한다.
4. 작성기, 메시지 목록, 방 헤더, 패널을 화면 컴포넌트로 분리한다.
5. 페이지는 방 ID와 기능 모듈을 조립하는 역할만 남긴다.

한 번에 전부 재작성하지 않는다. 이동 단계마다 기존 테스트와 수동 핵심 흐름을 통과시킨다.

### 상태 관리

- 서버 데이터와 임시 UI 상태를 구분한다.
- 메시지, 방, 캐릭터의 캐시 키와 갱신 규칙을 명시한다.
- 동일 엔터티를 여러 배열에 복제해 서로 다른 값이 남지 않게 한다.
- 정말 필요해질 때만 서버 상태 라이브러리를 추가한다. 도입 자체를 목표로 삼지 않는다.

### 오류 처리

- Supabase 호출의 오류를 조용히 무시하지 않는다.
- 사용자용 문구와 진단용 오류 정보를 분리한다.
- 치명적이지 않은 실패는 토스트와 재시도를 제공한다.
- 화면 전체가 깨지는 렌더링 오류를 잡을 오류 경계를 둔다.

### 완료 조건

- `Room.jsx`의 역할이 조립과 라우팅 중심으로 축소된다.
- 메시지·읽음·접속 상태 로직은 UI와 독립적으로 테스트할 수 있다.
- 주요 Supabase 작업의 실패가 모두 처리된다.
- 기능 분리 전후의 핵심 사용자 동작이 동일하다.

## 4단계 — 사용성 및 접근성

### 핵심 사용자 여정

다음 흐름을 설명 없이 완료할 수 있어야 한다.

1. 가입하고 로그인한다.
2. 첫 캐릭터를 만든다.
3. 방을 만들거나 초대 코드로 입장한다.
4. 사용할 캐릭터를 선택한다.
5. 첫 메시지와 이미지를 보낸다.
6. 다른 사용자의 메시지를 읽고 알림을 확인한다.
7. 나갔다가 다시 접속해 이어서 대화한다.

### 화면 기준

- 모든 드롭다운, 입력창, 버튼은 밝은·어두운 테마에서 충분한 대비를 가진다.
- 선택, 비활성, 포커스, 오류 상태를 색상 하나에만 의존하지 않는다.
- 터치 대상은 모바일에서 오작동이 적은 크기와 간격을 가진다.
- 키보드만으로 주요 기능을 사용할 수 있고 포커스가 보인다.
- 모달은 포커스를 가두고 닫힌 뒤 원래 위치로 돌려보낸다.
- 이미지에는 대체 텍스트 또는 장식 이미지 표시를 제공한다.
- 로딩 중 빈 화면 대신 현재 작업을 설명한다.
- 위험한 삭제는 대상 이름을 보여주고 확인을 받는다.

### 모바일

- 소프트 키보드가 메시지 입력창과 전송 버튼을 가리지 않는다.
- 긴 대사, 긴 이름, 큰 글꼴, 작은 화면에서 가로 스크롤이 생기지 않는다.
- 스크롤 중 새 메시지가 오면 사용자의 현재 읽기 위치를 빼앗지 않는다.
- 최신 위치 이동 버튼과 새 메시지 수를 제공한다.

### 완료 조건

- 대표 모바일 2종 크기와 데스크톱에서 핵심 여정이 통과한다.
- 브라우저 확대 200%에서도 핵심 조작이 가능하다.
- 자동 접근성 검사에서 치명적 오류가 없다.
- 라이트·다크 및 사용자 정의 테마에서 입력 요소 대비를 점검한다.

## 5단계 — PWA, 알림, 성능

### PWA와 업데이트

- 새 배포가 있을 때 사용자에게 새로고침 또는 업데이트 선택을 제공한다.
- Service Worker 캐시가 오래된 앱과 새 API 구조를 섞지 않게 버전을 관리한다.
- 오프라인에서 가능한 것과 불가능한 것을 명확히 표시한다.
- 설치 안내는 반복적으로 방해하지 않도록 상태를 저장한다.

### Push 알림

- 권한 요청 전에 알림이 필요한 이유를 설명한다.
- 거부, 미지원, 구독 만료, 브라우저별 제한을 구분한다.
- 로그아웃·탈퇴 시 현재 기기의 구독을 정리한다.
- 같은 계정의 여러 기기와 같은 브라우저의 계정 전환을 검사한다.
- 알림을 눌렀을 때 정확한 방으로 이동하고 인증 만료도 처리한다.

### 성능 목표

- 첫 화면에 필요하지 않은 무거운 기능은 지연 로딩한다.
- 메시지 수가 많아져도 전체 목록을 매번 다시 계산하지 않는다.
- 이미지 썸네일과 원본을 구분하고 적절한 크기로 전송한다.
- Realtime 채널과 이벤트 리스너가 화면 이동 후 남지 않게 한다.
- 5,000개 메시지가 있는 방에서 진입·스크롤·작성 성능을 측정한다.

### 완료 조건

- 배포 후 기존 설치 사용자가 정상적으로 최신 버전으로 전환된다.
- 알림 허용·거부·해제·계정 전환 흐름이 모두 동작한다.
- 장시간 사용 후 중복 Realtime 이벤트와 리스너 증가가 없다.
- 정한 성능 기준을 측정한 결과가 기록되어 있다.

## 6단계 — 운영과 사용자 안전

### 필수 운영 기능

- 사용자, 방, 최근 활동, 신고 현황을 최소 범위로 조회한다.
- 관리자 작업은 수행자, 대상, 시각, 사유를 감사 로그로 남긴다.
- 관리자 권한 부여·회수 절차를 문서화한다.
- 장애 시 읽기 전용 안내 또는 점검 공지를 표시할 수 있게 한다.
- 오류율, Edge Function 실패, DB 사용량과 저장소 사용량을 확인할 위치를 정한다.

### 사용자 안전

- 사용자 차단, 신고, 방 나가기, 초대 무효화 기능을 준비한다.
- 신고 대상에는 방, 사용자, 메시지와 최소한의 증거 정보를 포함한다.
- 차단 후 보이는 범위와 이미 공유된 방에서의 동작을 명시한다.
- 성인 대상 서비스라는 운영 방침과 허용되지 않는 콘텐츠 기준을 작성한다.
- 개인정보 처리방침, 이용약관, 문의·삭제 요청 경로를 제공한다.

### 백업과 복구

- Supabase 백업 제공 범위와 보존 기간을 확인한다.
- 주요 테이블을 별도로 내보내는 주기와 보관 위치를 정한다.
- 실수로 방이나 메시지를 삭제했을 때 가능한 복구 범위를 명시한다.
- 마이그레이션 실패 시 앱 버전과 DB 버전을 함께 되돌리는 절차를 연습한다.

### 완료 조건

- 운영자만 관리자 기능을 사용할 수 있고 작업 이력이 남는다.
- 신고 접수부터 검토·처리까지의 절차가 문서로 존재한다.
- 테스트 환경에서 백업 복원 연습을 한 번 이상 완료한다.
- 장애 대응 연락처와 상태 공지 방법이 정해져 있다.

## 7단계 — 테스트와 배포 품질문

### 테스트 층위

- **단위 테스트:** 읽음 위치 계산, 메시지 병합·중복 제거, 권한 판단용 순수 함수
- **컴포넌트 테스트:** 메시지 작성, 실패 재시도, 드롭다운, 모달, 캐릭터 선택
- **통합 테스트:** Supabase 로컬 환경에서 RLS, RPC, 마이그레이션
- **사용자 흐름 테스트:** 가입, 방 입장, 두 사용자 채팅, 재접속, 탈퇴
- **수동 탐색 테스트:** 모바일 키보드, PWA 설치, Push, 백그라운드 복귀

### 배포 전 자동 검사

모든 변경은 최소한 다음 검사를 통과해야 한다.

```text
의존성 고정 설치
정적 검사
단위·컴포넌트 테스트
사용자 앱 빌드
관리자 앱 빌드
마이그레이션 정합성 검사
RLS 권한 테스트
비밀정보 검사
```

`main`에는 검사를 통과한 변경만 합친다. 가능하면 미리보기 환경에서 확인한 뒤 프로덕션에 반영한다.

### 배포 후 확인

- 앱 첫 화면과 로그인
- 방 목록 조회
- 방 입장 및 메시지 송수신
- Realtime과 읽음 표시
- 이미지 업로드
- 관리자 로그인 차단·허용
- Service Worker와 최신 자산 로딩
- 브라우저 콘솔의 치명 오류

문제가 생기면 즉흥적으로 프로덕션 DB를 수정하기보다 이전 앱 배포 또는 준비된 보정 마이그레이션을 사용한다.

## 7. 우선순위 규칙

작업 후보는 다음 순서로 처리한다.

1. 데이터 유실 또는 권한 우회
2. 메시지 누락·중복·읽음 불일치
3. 로그인·방 입장 불가 같은 핵심 흐름 중단
4. 장애를 파악하거나 복구할 수 없는 문제
5. 모바일 사용 방해와 접근성 문제
6. 성능 저하와 코드 변경 위험
7. 편의 기능과 시각적 개선
8. 신규 기능

우선순위가 높은 결함이 열려 있는 동안 같은 영역의 신규 기능을 추가하지 않는다.

## 8. 변경 작업 표준 절차

모든 작업은 다음 순서를 따른다.

1. 사용자에게 보이는 문제와 재현 조건을 한 문장으로 정의한다.
2. 관련 코드, DB 정책, 실제 배포 동작을 읽기 전용으로 조사한다.
3. 예상 원인과 영향을 받는 기능을 기록한다.
4. 기존 동작을 보호할 테스트 또는 검증 절차를 만든다.
5. 가장 작은 변경으로 수정한다.
6. 자동 검사와 관련 수동 검사를 수행한다.
7. 변경 전후와 남은 위험을 검토한다.
8. 기능 단위로 커밋한다.
9. 배포 후 실제 환경에서 확인한다.
10. 문서와 알려진 문제 목록을 갱신한다.

## 9. Git 및 커밋 규칙

- 작업 시작 전 `git status`로 사용자 변경을 확인한다.
- 사용자 변경을 임의로 되돌리거나 덮어쓰지 않는다.
- 기능, 리팩터링, DB 마이그레이션, 문서를 가능한 한 별도 커밋으로 나눈다.
- 생성물과 임시 파일은 커밋하지 않는다.
- 커밋 제목은 결과가 드러나게 작성한다.

예시:

```text
fix: reconnect 후 읽음 상태를 서버 기준으로 보정
test: 방 외부 사용자의 메시지 접근을 차단하는 RLS 검증
refactor: Room의 메시지 구독 로직을 전용 훅으로 분리
docs: 배포 후 점검 절차 추가
```

DB 변경은 마이그레이션 파일과 영향을 받는 앱 코드를 같은 작업 묶음으로 추적하되, 배포 순서가 필요하면 설명에 명시한다.

## 10. DB 마이그레이션 규칙

- 이미 적용된 마이그레이션 파일은 수정하지 않고 새 보정 마이그레이션을 추가한다.
- 테이블·컬럼 추가는 가능한 한 nullable 또는 안전한 기본값으로 시작한다.
- 인덱스는 실제 조회 패턴과 실행 계획을 근거로 추가한다.
- RLS를 켠 직후 필요한 정책과 권한을 같은 마이그레이션에 둔다.
- `security definer` 함수는 소유자, `search_path`, 실행 권한, 내부 권한 검증을 함께 검토한다.
- 마이그레이션은 빈 DB와 기존 데이터가 있는 DB 양쪽에서 검증한다.
- 앱이 구버전 DB 또는 신버전 DB와 잠깐 공존할 수 있는 배포 순서를 설계한다.
- 운영 DB에 대시보드로 수동 변경한 경우 즉시 동일한 마이그레이션으로 기록한다.

## 11. 기능별 완료 정의

하나의 기능은 아래 항목을 모두 만족해야 완료다.

- 로딩·빈 상태·오류·재시도 상태가 있다.
- 모바일과 데스크톱에서 확인했다.
- 키보드와 기본 접근성을 확인했다.
- 권한 없는 직접 API 호출을 검사했다.
- 자동 테스트 또는 반복 가능한 검증 절차가 있다.
- 앱과 관리자 앱 빌드가 통과한다.
- 실제 배포 환경에서 확인했다.
- 관련 문서를 갱신했다.
- 남은 위험과 후속 작업을 기록했다.

## 12. 베타 진입 기준

다음 조건 전에는 외부 사용자를 초대하지 않는다.

- 치명도 높은 데이터 유실·권한 결함이 0건이다.
- 두 사용자 실시간 채팅과 읽음 표시 테스트가 안정적으로 통과한다.
- 탈퇴, 신고, 차단, 문의 경로가 준비되어 있다.
- 개인정보 처리방침과 이용 기준을 확인할 수 있다.
- 운영자가 장애와 사용량을 확인할 수 있다.
- 백업과 최소 복구 절차가 검증되었다.
- 배포 실패 시 되돌릴 수 있다.
- 알려진 제한사항을 베타 사용자에게 안내할 수 있다.

## 13. 고도화 기간에 추적할 지표

결제 지표는 제외하고 제품 신뢰성과 사용성을 측정한다.

- 가입 후 첫 방 입장 성공률
- 방 입장 후 첫 메시지 전송 성공률
- 메시지 전송 실패율과 재시도 성공률
- Realtime 재연결 횟수와 복구 실패율
- 읽음 상태 보정 발생 횟수와 최종 수렴 시간
- 페이지 오류와 처리되지 않은 API 오류 수
- 이미지 업로드 실패율
- 가입 후 1일·7일 재방문율
- 방별 주간 활성 사용자 수
- 신고 건수와 처리 시간

사용자 대화 내용 자체를 분석 지표로 수집하지 않는다. 꼭 필요한 이벤트만 수집하고 개인정보 처리방침에 반영한다.

## 14. 권장 목표 운영 방식

전체 작업은 하나의 거대한 목표가 아니라 아래 세 목표로 순차 실행한다.

### 목표 A — 안전한 기준점과 핵심 신뢰성

- 현재 변경 보존
- DB·RLS 현황 일치
- 메시지와 읽음 상태 안정화
- 핵심 자동 테스트 구축

### 목표 B — 구조와 사용자 경험

- `Room.jsx` 점진 분리
- 공통 오류 처리
- 모바일·접근성 개선
- PWA와 알림 안정화

### 목표 C — 베타 운영 준비

- 관리자 권한과 감사 로그
- 신고·차단·탈퇴
- 백업·복구와 모니터링
- 베타 진입 점검 및 운영 문서

각 목표가 끝날 때 실제 배포 환경을 검증하고 다음 목표의 범위를 다시 확정한다.

## 15. 첫 번째 목표에 사용할 문구

> 기존 기능과 사용자 데이터를 보존하면서 IDEA 앱의 안전한 개발 기준점을 확보하고, 두 사용자의 실시간 메시지 송수신과 읽음 상태가 네트워크 단절·탭 복귀·재접속 후에도 정확하게 수렴하도록 개선한다. 현재 미커밋 변경을 먼저 분류·보존하고, 실제 Supabase 스키마와 마이그레이션의 차이를 확인하며, 메시지·읽음·RLS 핵심 경로에 자동 검증을 추가한다. 결제, 구독, 유료 기능 제한, 위키 연동, 대규모 디자인 변경은 이번 목표에서 제외한다.

### 첫 번째 목표의 완료 조건

- 현재 작업이 기능별 커밋으로 안전하게 보존된다.
- 앱과 관리자 앱이 재현 가능하게 빌드된다.
- 메시지 누락·중복·전송 실패가 명시적으로 처리된다.
- 읽음 상태가 여러 기기와 재접속 뒤에도 뒤로 가지 않고 서버 상태에 수렴한다.
- 핵심 RLS 허용·거부 테스트가 통과한다.
- 관련 자동 검사와 배포 후 점검 기록이 남는다.

## 16. 의사결정 금지선

다음 행동은 별도 합의 없이 하지 않는다.

- 운영 데이터 삭제 또는 대량 수정
- 인증 방식 교체
- Supabase 프로젝트 교체
- 공개 URL과 라우팅 구조 변경
- 저장소 공개·비공개 상태 변경
- 호스팅 제공자 이전
- 관리자 권한 추가·회수
- 개인정보 수집 범위 확대
- 사용자 경험이 달라지는 대규모 UI 재설계
- 결제·구독 관련 구현

이 금지선은 작업을 막기 위한 것이 아니라 장기 목표가 현재 요청의 권한 범위를 임의로 넓히지 못하게 하기 위한 것이다.
